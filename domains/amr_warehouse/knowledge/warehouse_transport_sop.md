# 仓储物料转运作业 SOP

> 本文档是 P0-07 仓储 RAG 的冻结知识基线之一。  
> 适用于“单受控 Agent 编排 4 台 AMR，在二维仓库中完成 pickup → transport → dropoff”的 P0 首发场景。  
> LLM 负责目标理解、计划生成、工具选择和异常处置建议；任务分配、路径规划、计划合法性与安全裁决由确定性程序负责。

## 1. 适用范围

P0 固定场景：

- 30×20 二维栅格地图。
- 4 台同构差速驱动 AMR。
- 6 个取货点、6 个交付工位、2 个充电站。
- 地图包含固定障碍、单向/窄通道和临时禁行区。
- 订单包含 pickup、dropoff、优先级、发布时间、截止时间和可选前置关系。
- V1 不包含真实底盘、ROS 2、SLAM、感知和电机控制。

## 2. 标准转运流程

1. 接收自然语言订单。
2. 转换为结构化 `TaskContract`。
3. 校验执行所需字段；缺少关键字段时澄清或拒绝，不允许模型猜测。
4. 检索相关 SOP/设备规则，并保留引用。
5. Planner 生成结构化任务 DAG。
6. Validator 检查 Schema、依赖、权限、预算和业务/运动约束。
7. 获取最新车队、工位、通道和地图状态。
8. Hungarian 分配器完成当前滚动周期的 AMR—订单匹配。
9. A* 与时空预约表生成多 AMR 路径。
10. `fleet_plan_validator` 再检查时间窗、载荷、电量、禁行区、工位容量、顶点/边冲突和安全距离。
11. 只有验证通过的计划才能派发到 Python 仿真器。
12. 执行过程中持续读取真实 Observation。
13. Verifier 判断继续、局部重规划、审批、Fallback 或结束。
14. 完成后持久化证据、计划版本、工具调用、最终状态和指标。

## 3. 订单与调度边界

### 3.1 必须提供的订单信息

每个订单至少需要：

- 订单/物料标识。
- `pickup`。
- `dropoff`。
- 优先级。
- 发布时间。
- 截止时间。
- 前置任务（如有）。

缺少 pickup、dropoff、截止时间等执行关键字段时，不得自行填充默认值。

### 3.2 P0 固定调度边界

- 每个滚动调度周期内，一台 AMR 最多新分配 1 个运输订单。
- V1 不做一台 AMR 同时批量承载多个独立运输订单。
- 优先级的具体编码由 `TransportOrder` 数据契约定义；知识文档只规定“优先级可影响分配与排序，但不能绕过安全约束”。
- AMR 最大载荷等数值型设备参数由运行配置/数据契约提供，Validator 是执行时权威；RAG 不自行生成数值。

## 4. 任务分配

P0 使用 Hungarian 算法完成 AMR—订单匹配。

代价至少考虑：

- 到取货点距离。
- 迟到风险。
- 订单优先级。
- 电量风险。
- 当前负载。

不可行组合必须返回不可行原因，不能仅通过“给一个很大代价”后仍允许派发。

## 5. 路径规划与交通约束

C++ A* 路径状态使用 `(x, y, heading, t)`，代价包含移动、转向和等待。

多车规划通过 `(cell, t)` 与 `(edge, t)` 预约避免：

- 顶点冲突。
- 交换边冲突。

路径不得：

- 越界。
- 穿越固定障碍。
- 进入当前生效的禁行区。
- 逆行通过单向通道。
- 违反车队计划验证器的安全距离。

无安全可行路径时应返回不可行，不允许忽略硬约束继续执行。

## 6. 计划验证

计划派发前至少检查：

- 任务依赖。
- 时间窗。
- 载荷。
- 电量安全余量。
- 禁行区。
- 工位容量。
- 顶点/交换边冲突。
- 安全距离。
- 工具权限。
- 参数 Schema。

**LLM、用户文本和人工审批均不能直接把非法计划变成合法计划。**

## 7. 执行与完成判定

执行后续决策必须基于真实 Observation，而不是模型“认为已经完成”。

运输任务完成至少需要：

- 取货动作已被仿真/执行环境记录为完成。
- 交付/卸载动作已被仿真/执行环境记录为完成。
- 订单完成条件满足。
- 未违反硬安全约束。
- 对应证据、计划版本和最终状态已经记录。

P0 不额外模拟独立的人工“签收系统”；装载/卸载具体持续时间属于仿真运行配置，不作为 RAG 固定知识。

## 8. 异常处理摘要

### 8.1 AMR 离线
保留已完成任务与 Effect Ledger，只失效引用该 AMR 的未完成子图；获取真实状态后再决定重新分配、重规划、Fallback 或人工处理。

### 8.2 通道封闭
引用封闭单元格/边的未完成路径立即失效；只重规划受影响部分，新计划必须重新验证。

### 8.3 工位占用
根据当前状态等待、调整未执行任务或局部重规划；不得无限等待。

### 8.4 工具超时
超时既不等于成功也不等于失败。对副作用工具必须先检查 Effect Ledger 和真实状态，再决定是否重试。

### 8.5 计划不可行
可尝试重新分配、调整顺序和局部重规划；不得修改硬约束强行通过。

## 9. 禁止事项

- 未经确定性验证直接派发。
- LLM 直接控制底盘。
- 为赶截止时间进入禁行区。
- 忽略顶点/交换边冲突。
- 缺失关键字段时自行猜测。
- 把模型文本当作完成证据。
- 通过 Prompt 绕过权限、Schema 或 Validator。
- 不受控地重复副作用。
- 向正常 Agent 暴露故障注入工具。
- 执行任意 Shell、任意 SQL、任意外部 HTTP 或模型生成代码。
